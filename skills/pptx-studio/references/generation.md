# Complete presentation generation

Read for a new deck or substantial rebuild. For a narrow repair, use the requested module and shared verification without repeating the entire creation process.

## Brief and materials

Identify the purpose, audience, viewing situation, language, required output and supplied constraints. A presentation may aim to explain, teach, persuade, document, entertain, tell a story or support a decision; multiple goals can coexist. Consult [scenarios.md](scenarios.md) when a purpose needs a different narrative or evidence standard.

Read the actual materials: documents for claims and context, data for quantities, screenshots for real interfaces, images for visual evidence, and reference decks for either content or design as requested. Preserve the distinction between a design reference and a factual source. Resolve contradictions or missing decisive evidence before using a strong claim. A topic alone can support a useful introductory deck; company-specific achievements, quotations, study results and product features require sources.

Honor exact page counts. An N-slide request normally means N total, including a cover if one is useful. A one-page request need not have a separate cover. Duration is a pacing constraint, not a universal slides-per-minute formula. For self-reading material, retain enough context on the page; for live delivery, reserve supporting explanation for notes when appropriate.

## Storyline and page plan

Choose an organizing logic that serves the purpose: decision and supporting evidence, question and explanation, learning progression with practice, research argument, user journey, chronology, visual story, or another suitable structure. Preserve a required outline while improving transitions where authorized. Avoid automatic sections such as company introduction or market size when they do not help the requested task.

Build a compact internal page plan before authoring. Useful fields are page role, title or subject, essential visible content, source/evidence, visual representation, asset needs, and speaker support where applicable. This is a working plan, not a required user-facing form or a reason to stop for approval. Save it separately when the task is large enough that it helps iteration.

Give each slide a deliberate role: orientation, explanation, finding, demonstration, practice, story moment, summary, reference, or a role the task requires. A photographic story or exercise does not need a claim-based title on every page. Separate essentials from optional detail without losing requested information. Allocate space to evidence before decoration.

## Visual system and variation

Inspect a supplied template first. Otherwise choose a coherent visual direction from the brief: typography, palette, grid, image treatment, diagrams and density. Read [style.md](style.md). User branding, a specific aesthetic or custom colors take precedence over optional defaults.

Use page structures that fit the content: a large photo, an annotated figure, a worked example, native chart, editable table, visual comparison, diagram, quiet text page or another suitable composition. Read only the modules needed by the work. [layout-recipes.md](layout-recipes.md) supplies a few useful structures; it is not a closed layout catalog.

Vary compositions when the page roles differ while retaining hierarchy and spacing. Avoid a repeated title-plus-cards pattern for unrelated material. A sequence of dense reference pages may be correct for a reading deck; a sparse keynote needs a different rhythm. Keep distinctions visible at the intended viewing size and in all required languages.

## Assets and authoring

Plan image proportions and placement before retrieving or generating assets. Use authentic screenshots for actual product behavior and sourced imagery for real evidence. When an illustration is conceptual, keep that distinction clear. Read [images.md](images.md) for asset handling. If icons help, use [icons.md](icons.md); they are optional rather than a default quota.

Keep analytical charts, tables, labels and intended diagrams editable where supported. Match source units and qualifiers. Use the selected backend's actual capabilities; consult [backends.md](backends.md) when choosing one. A collection of full-slide images does not meet an editable-deck request.

If several constraints conflict, preserve the user's hard requirements and resolve the smallest remaining design choice. Clearly flag essential missing evidence. Finish independent authorized work while a missing asset is unresolved. Do not quietly invent screenshots, metrics or customer testimonials to complete a layout.

## Speaker support

When useful for a live presentation or requested, place supporting explanation, examples and transitions in slide notes. Keep the notes complementary to the visible page. Teaching notes may include the answer to a practice question; research notes may retain methodological qualifications; a keynote may need concise speaking cues.

Provide timing only when a duration or pacing plan is available, and distinguish a suggested speaking duration from automatic slide advance. Do not invent interactions, venue conditions or claimed speaking speed. Do not add an interactive presenter runtime or autoplay merely because notes were requested.

## Completion

Read [verification.md](verification.md). Check the whole deck for coverage, source accuracy, language, slide count, coherent visual system, narrative flow and usable output. Inspect actual final-file renders for layout; check selected edits against the source for preservation. Retain explicit limits when a renderer or target application is unavailable.

Deliver the requested presentation, any requested notes or additional formats, and a concise account of unresolved issues. Internal page plans and validation logs stay separate from audience-facing slides unless the user asks for them.
